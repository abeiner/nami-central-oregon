# Taking the sponsorship app into production

The Regional Director owns the offers, sponsor communications and decision to open intake. A technical maintainer owns GitHub releases, Azure settings and recovery. Name a backup maintainer who can sign in independently. Keep their contact details and recovery instructions in NAMI’s password manager. [Rotate the staff passcode](#3-rotate-the-staff-passcode) · [Maintenance calendar](#4-keep-it-running)

## 1. Put GitHub and Azure under NAMI’s control

| What | Current demo | Production handoff |
| --- | --- | --- |
| Code and releases | A private, individually owned GitHub repository publishes to the demo on pushes to `main`. At handoff review, `main` was unprotected and there was no GitHub deployment environment. | Create a private repository in NAMI’s GitHub organization from the approved source. Keep the demo repository available for practice. Give the maintainer and backup individual accounts with MFA. Routine staff work happens in the desk. |
| Deployment | The [workflow](../.github/workflows/publish.yml) builds the sponsor PDF, React site and managed Node API. The target is selected by the deployment credential. | In the production repository, start with Actions disabled. Set the deployment secret referenced by the workflow to the **production app’s own deployment token** before enabling releases. Open a pull request for changes and record the approved commit and successful run. |
| Hosting and data | The demo has its own Azure app, storage and staff credential. | Use an organization-owned Azure subscription, a separate Static Web App, private Blob Storage, a production subdomain and NAMI-controlled DNS. Give the maintainer and backup access scoped to these resources. [Infrastructure and monthly budget](../README.md#production-infrastructure-and-budget) |

For a low-cost release process, give production write access only to the release maintainers. Have one review the other’s change and use a manually triggered production deploy. **The current workflow also triggers on push.** Remove that trigger in the production copy if choosing manual releases, and dispatch from reviewed `main`. Add a build-only pull-request check with no deployment credentials. Where the private repository’s plan supports it, protect `main`, require that check and a review, and restrict a GitHub deployment environment to the release branch. [Branch protection availability](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) · [GitHub environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)

**What belongs in GitHub.** Keep source, dependency lockfiles, the release workflow, and the approved public catalog in the private repo. The workflow deploys to existing Azure resources. To make the infrastructure reproducible, a next step is to version a Bicep template for the app, storage account, private container, retention and budget alert. Keep actual credential values in Azure settings or the password manager. Keep sponsor records, logos submitted by businesses, invoices and backups in approved private storage.

## 2. Open real sponsor intake

1. **Director** — Sign off on prices, limited placements, the agreement, payment instructions and who reconciles funds. Confirm NAMIWalks levels with the walk organizers and approve recognition wording for Mental Health Champions. Confirm the reply mailbox and how staff handle contact details and logo permissions. An inquiry opens a prospect. A signed standard commitment creates an invoice.
2. **Maintainer** — Run one fictional inquiry and one commitment against isolated test storage. Follow the invoice through payment recording, welcome draft and benefit delivery. Before the first live deployment, set production `SPONSOR_BLOB` to the clean private store and create its `sponsorship` container. Set `PUBLIC_ORIGIN`, `PAYMENT_INSTRUCTIONS` and a new production `ADMIN_KEY`. Use `SPONSOR_DEMO=0` for the **first access to the clean production store**. A store already initialized in demo mode retains its fictional records when the flag changes. [Configuration checklist](../README.md#before-the-first-real-sponsor)
3. **Maintainer** — Update the absolute sharing URLs in [the sponsor homepage](../web/index.html) and [the showcase](../web/public/launch/index.html). Pass the production origin to [the bundled guide generator](../scripts/build-guide.py) with `--site-url` in the production workflow. Verify the PDF link and QR code open the production builder.
4. **Together** — On the production hostname, check `/api/health` reports `demo: false`, open the live guide at `/api/guide.pdf`, and sign in at `/admin` in a fresh private window. Confirm the real desk opens with the expected starting records and a request to `/api/admin/templates` without a key gets HTTP 401. A tab that opened `/admin?demo=1` stays in browser-only practice mode. If you see the demo banner, open a fresh private session for the real desk. Record the release commit, verified hostname, date and sign-off before sending invitations.

## 3. Rotate the staff passcode

The desk and authorized MCP assistants share one server-side `ADMIN_KEY`. Anyone holding it has the same staff permissions. Rotate it at handoff, when someone with access leaves, or immediately after suspected disclosure. Review the holder list quarterly. If NAMI needs individual revocation, MFA at the desk or attribution of each edit, plan a named staff sign-in before granting access more widely.

1. **Prepare.** The maintainer generates a random passcode of at least 32 URL-safe characters in NAMI’s password manager. For a planned rotation, tell staff when to save open edits. For a departure, remove the person’s vault and administrative access, and account for any sponsor exports on their devices. Keep a backup maintainer able to reach the production app settings.
2. **Replace.** In the Azure portal, open the **production** Static Web App, then **Settings → Environment variables → Production**. Edit only `ADMIN_KEY`, apply the value and save. Keep the new value out of GitHub, screenshots and chat. [Azure application settings](https://learn.microsoft.com/en-us/azure/static-web-apps/application-settings)
3. **Verify both keys.** After the setting takes effect, the **old** passcode must fail and the **new** one must open `/admin` in a fresh private window. For a read-only API check, request `GET /api/admin/templates` with the `x-admin-key` header. Expect **401 with the old key, 200 with the new key, and 401 without a key**. If results vary, verify the hostname and environment, allow the API workers to reload, and repeat. If staff are locked out, the backup maintainer can set a fresh value through Azure and repeat these checks.
4. **Reconnect.** Staff sign out of old tabs and sign in again. A tab can still display previously loaded records. For each approved assistant, update `NAMI_MCP_TOKEN`, open a new terminal with that environment and restart the client. Verify a read-only MCP connection using `x-admin-key`. Store only the environment-variable reference in client configuration. Share the new passcode through the vault and record the date, operator and outcome. [Assistant connection check](assistant.md#other-clients)

The **deployment token** releases code, the **storage credential** grants access to records, and private **invoice links** have per-invoice access tokens. A staff passcode rotation requires no code release. Existing invoice links continue to work for anyone who holds them. Report a forwarded link to the maintainer because the desk has no per-link revocation control. For an exposed deployment token, reset it on the Azure app, replace the matching GitHub Actions secret and verify a release. [Azure deployment token reset](https://learn.microsoft.com/en-us/azure/static-web-apps/deployment-token-management)

**Before connecting an AI assistant to production**, the director approves who may use it and how sponsor data may be handled. Use the desk for names, addresses and private invoice links. The MCP email preview omits private personalization, but anyone with the connector’s credential has staff access. [Assistant data handling](assistant.md#run-a-check-in)

## 4. Keep it running

| When | Owner | Action |
| --- | --- | --- |
| Each business day during outreach | Director | Set a recurring calendar reminder to check **Sponsors** and **This week**. New inquiries and commitments appear silently. Send the sponsor a personal reply or the private invoice link from NAMI’s mailbox that day. Their confirmation page is stored in their browser tab. |
| Weekly | Director | Reconcile payments against accounting or Little Green Light, record verified funds in the desk and complete delivered benefits. The desk tracks promises and renewals. Recording payment here does not update accounting. [Staff playbook](staff-playbook.md) |
| Monthly | Maintainer | Review Azure costs and storage growth against the budget. Check the site, live PDF and staff sign-in, the last successful release, and dependency and runtime updates. Apply updates in a branch and rehearse them against fictional data. |
| Before each release | Maintainer | Record the last known-good commit and check data-format compatibility. Build with the checked-in lockfiles. Test a direct visit to `/admin` in Chrome or Edge with common content filters enabled, then check the public builder, PDF and a protected endpoint after release. |
| Quarterly and at handoff | Maintainer and backup | Review GitHub, Azure, DNS, vault and assistant access. Test recovery of the ledger, catalog and one logo in restricted, isolated storage. The director reviews upcoming renewals and remaining placements. |

**If a limited placement shows as full**, the director checks the signed records and contacts the sponsor before promising the slot to another business. An unpaid signed commitment reserves capacity. For a confirmed cancellation or junk submission, the director documents which record to release and checks payment with accounting. The maintainer can then set `{"status":"lapsed"}` through the authenticated `PATCH /api/admin/sponsors/{id}` route, which keeps the record and releases its placement. The desk can display lapsed records but has no control for setting this status.

**If a release breaks the site**, revert the faulty change through a reviewed pull request and deploy against the same production settings and store. Confirm the public guide and staff desk work again. Before reverting a data-format change, check compatibility and preserve newer submissions. If the problem is a price or benefit edited in **Program content**, correct it there. A saved catalog takes precedence over the bundled file and publishes immediately. Verify the live PDF after saving.

**If records go missing**, pause intake and staff edits before a live data repair. Preserve the current store, recover the relevant version or protected backup into a separate private location, and compare with accounting and recent commitments. Restore only after the director reconciles newer activity. The `sponsorship` container includes `staff/ledger.json`, the edited catalog at `staff/content.json`, `logos/` and daily `metrics/` blobs. A CSV export covers only part of this data. Before launch, enable blob and container soft delete, configure blob versioning with expiry for old versions, and test a restore. Agree how much data NAMI can afford to lose and whether it needs an independent backup for loss of the storage account. [Azure storage recovery options](https://learn.microsoft.com/en-us/azure/storage/blobs/data-protection-overview)
